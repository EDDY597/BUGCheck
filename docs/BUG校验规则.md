## 1. 数据源

### 1.1 BUG 数据

- **平台**：OpenProject（默认 `https://op.crprobot.com`，可在设置中改列表页 URL）
- **列表页**：默认 `work_packages?query_id=4351`
- **筛选条件优先级**：
  - URL 里带 `query_props`（页面上调好的筛选）→ **以 URL 为准**，工具按它拉取，
    数量与你在页面上看到的**一致**；排序也跟随 URL 的 `t`
  - URL 不带 `query_props` → 用查询自身在 OpenProject 保存的条件（取 `_links.results`）
- **类型过滤**：无论走哪条路，都会补上一个 `type` 白名单（`7=Bug`, `37=建议`, 以及测试/文档编写等需识别类型的 ID）
  - 旧版会**剥掉** type 过滤，导致把「测试」「文档编写」等无关工作项也拉进来 → 显示数量偏多
  - 现在既不剥掉、也不写死：URL/查询已限定类型就**原样保留**，没限定才补白名单
  - 实际采用的筛选条件原文**只写到服务端控制台**（`🔎 按 URL 中的筛选条件拉取：…`），不推送到前端页面
- **列表枚举走 REST API**（`GET /api/v3/queries/{id}` → 取其 `_links.results` → `pageSize=500` 翻页取全），
  类型取自 `_links.type.title`（数据库外键，**权威**）
  - 旧实现只读列表页**第一页**（分页由 `query_props.pp` 控制，默认 20）→ **超过 20 条会静默漏掉**
  - API 不可用时**降级**为页面抓取（仅第一页），并在日志中明确告警
- **详情**：仍由 Playwright 抠详情页 DOM（描述、模块、关联工艺、journal 等）
- **类型判定优先级**：API `type.title` → 列表页类型提示 → 详情页角标/标题识别
  - 详情页识别会受标题措辞影响，因此**能被 API 覆盖时一律以 API 为准**
  - 父级是「需求」不影响子单类型：查询只返回匹配项本身，父级仅作 `_links.parent` 引用存在，不会被校验
- **登录**：设置中的账号/密码；cookie 缓存于 `cookies.json`（API 请求复用同一 context 的会话）

### 1.2 模块规格

- 来源：`data/规格.json`（用户可编辑，对应「CrobotpOS测试规格」三级层级）；
  缺失/损坏时回退内置 `src/spec-tree.default.json`
- 匹配时忽略括号后缀：`送丝控制（R4）` → `送丝控制`

### 1.3 工作包类型

| 类型 | 校验 |
|:----:|------|
| **BUG** | 全部 5 项规则 |
| **需求** | 跳过（结果中隐藏） |
| **建议** | 精简：受理人、关联产品、负责人、发现BUG版本、模块、Release Phase、版本（Release Phase 单选时放宽为「非 Product Release」，并标红提示需自行判断） |
| **文档编写** | 跳过 BUG 规则（不进结果表） |
| **测试** | 跳过 BUG 规则（不进结果表）——测试类型单不是缺陷单 |
| **未知类型** | 类型未识别 → 跳过并在日志中列出，**不再默认按 BUG 校验** |
| **详情获取失败** | 标为不通过并提示重试（不用「需求」占位） |

> 代码中以 `VALIDATED_TYPES = ['BUG','建议']` 与 `SKIP_TYPES = ['需求','其他','文档编写','测试']` 统一维护；
> 类型别名字面量集中在 `TYPE_ALIASES`，未识别类型常量 `UNKNOWN_TYPE = '未知类型'`。

### 1.4 类型别名与拼写容错（`TYPE_ALIASES`）

| 类型 | 识别别名 |
|------|----------|
| 建议 | 建议、Suggestion、Improvement、优化建议 |
| 需求 | 需求、Requirement、**Feature（含拼写变体 featrue / fetaure 等）**、User Story、Story |
| 文档编写 | 文档编写、文档、Documentation、Docs、Doc |
| 测试 | 测试、测试用例、测试执行、**用例、用例编写、测试用例编写、用例设计**、Test、Testing、Test Case、Testcase |
| 其他 | 其他、Other、Task、任务、Epic、史诗、Milestone、里程碑、Phase、阶段、Support、支持 |
| BUG | Bug、BUG、缺陷、Defect、Issue、Fault |

- **英文拼写容错**：纯英文别名按「相邻字符对折叠」比较，`featrue` / `fetaure` 均归一到 `feature`
- **中文**：忽略空白后精确匹配（不做模糊匹配，避免误伤）
- **识别顺序**：整串类型名 → 尾缀括号 `xxx（测试）` → 前缀 `【测试】/测试：/Test:` → 英文词前缀
- 新增类型只需往 `TYPE_ALIASES` 加一行，两处调用点自动生效

## 2. 类型分支

- **BUG**：规则 1–5  
- **需求**：不校验（结果中隐藏）  
- **建议**：见 1.3 精简字段；Release Phase：发现BUG版本多选 → `Product Release`，单选 → **非 `Product Release`**（原来固定期望 `DEV`，因单选/多选靠分隔符判断存在误判风险，已放宽为只排除 `Product Release`，并在结果表标红提示「需自行判断」）；版本(Version) → `Product backlog`  
- **文档编写**：不跑 BUG 规则，不进结果表  
- **测试**：不跑 BUG 规则，不进结果表  
- **未知类型**：不跑 BUG 规则，不进结果表，日志中 `⚠️ 有 N 个单子类型未识别，已跳过校验` 并列出 ID  
- **结果表**：网页只显示 **BUG** 和 **建议**
- **类型识别**：类型角标 / 「类型」属性优先，标题仅兜底识别各类型；避免标题里出现「缺陷/Bug」把需求误判成 BUG
- **兜底策略（重要）**：角标/属性/标题/列表提示**全部认不出来时标记为「未知类型」并跳过**，
  不再 `type = 'BUG'`。这样新类型不会静默变成假的不通过，而是在日志里暴露出来等着补 `TYPE_ALIASES`。

## 5. 规则3：版本迭代（BUG）

### 5.1 控制器版本

从描述「重现条件 → 软件版本 → 控制器版本」提取，形如 `CRA9-x.y.z-suffix`。

### 5.2 后缀 → Release Phase / Version

| 后缀包含 | 类型 | Release Phase | Version |
|----------|------|---------------|---------|
| `pre` / `rc` | RC | RC Release | Bug backlog |
| `alpha` | Alpha | Alpha Release | Bug backlog |
| `feature` / `feat` | Feature | Dev | 与控制器版本 `1.x.y` **前两段一致**的版本（见下） |
| `beta` | Beta | Beta Release | Bug backlog |
| 其它（无上述关键词） | Stable | **Product Release** | **Bug backlog** |

#### feature 版本的 Version 放宽规则

控制器版本为 `1.x.y` 时，Version **允许填 `1.x.z`** —— 即**前两段必须一致，第三段可不同**：

| 控制器版本 | Version | 结果 |
|-----------|---------|------|
| `1.15.0` | `1.15.0` | ✓ 完全相同 |
| `1.15.0` | `1.15.1` | ✓ 同属 `1.15.x`，允许 |
| `1.15.0` | `1.15.9` | ✓ 同属 `1.15.x`，允许 |
| `1.15.0` | `1.16.0` | ❌ 小版本不同 |
| `1.15.0` | `1.14.9` | ❌ 小版本不同 |
| `1.15.0` | `2.15.0` | ❌ 主版本不同 |
| `1.15.0` | `1.15` | ❌ 格式不完整（须 `x.y.z`） |

命中放宽时输出：`✓ 版本 = 1.15.1（与控制器版本 1.15.0 同属 1.15.x，允许）✓`

> 实测依据：项目内 `1.14.13 → 1.14.14`（#65048，黄贵良人工改）也是同前两段、第三段递增，
> 说明这种填法在业务上被认可，非本次放宽凭空引入。

#### ⚠️ 放宽**仅限 feature**（rc / alpha / beta 不适用）

**放宽只作用于 `feature` 后缀**。其余类型仍然**必须**填 `Bug backlog`：

| 控制器版本 | 版本类型 | Version 规则 | `1.15.1` 的判定 |
|-----------|---------|-------------|----------------|
| `…-feature_xxx` | feature | 前两段一致即可 | ✓ 允许 |
| `…-rc.15` | rc | **必须 `Bug backlog`** | ❌ 不通过 |
| `…-pre.1` | pre | **必须 `Bug backlog`** | ❌ 不通过 |
| `…-alpha.3` | alpha | **必须 `Bug backlog`** | ❌ 不通过 |
| `…-beta.2` | beta | **必须 `Bug backlog`** | ❌ 不通过 |
| `…`（无后缀） | stable | **必须 `Bug backlog`** | ❌ 不通过 |

语义依据：rc / beta 属**预发布**，Version 应指向 `Bug backlog`（尚未进入正式迭代），
不应直接挂到某个正式版本号上。**改动此规则前请先确认业务规范。**

> 代码位置：`validate-server.js` 中 `if (vt === 'feature')` 分支内的 `versionMatchesCtrl()`。
> 其它分支为 `bug.version.toLowerCase() !== 'bug backlog'`。

### 5.3 版本链路（可配置）

默认从新到旧：`1.16.0 → 1.15.0 → 1.14.11 → 1.12.10`  
在 **⚙ 设置 → 版本链路** 中修改；计划任务 `run-once.vbs` 会读取 `data/login_config.json` 里同一配置。

| 条件 | 要求 |
|------|------|
| 当前控制器版本 | 必须出现在「发现BUG版本」 |
| 「能否重现」中 **否掉** 的旧版本 | **不能** 出现在「发现BUG版本」 |
| 未否掉的旧版本 | **必须** 出现在「发现BUG版本」 |

### 5.4 龙燕修改字段跳过校验

活动区 journal 操作人含「**龙燕**」或「**黄贵良**」时，解析其每条变更，抽出**被改过的字段名**，例如：

```
2026-09-12 11:31  版本 已从 Bug backlog 更改为 1.15.0   → 跳过「版本」
```

**规则（取代原先「有龙燕就放宽 Version」的整段豁免）：**

- 同一条活动可能含多个字段，按 `；` 拆分后逐个识别字段名  
  例：`受理人 已从 A 更改为 B；版本 已从 X 更改为 Y；Dev ...` → 跳过 受理人、版本、Dev
- **龙燕/黄贵良改过什么，就跳过什么**；没改过的仍按原规则校验
- 结果中不展示「受理人」「Dev」的修改明细（仍参与跳过）
- 其它字段以 `⏭️ 字段已被龙燕修改，跳过校验` 体现，并列出修改记录（输出文案仍用「龙燕」）

| 龙燕/黄贵良改过的字段 | 跳过的校验 |
|----------------|------------|
| 版本 / Version | 版本(Version) 期望值检查 |
| Release Phase | Release Phase 与控制器版本匹配 |
| 发现BUG版本 | 填写/格式，以及版本链路覆盖/排除 |
| 负责人 | 人员规则中的负责人 |
| Tester | 人员规则中的 Tester |
| 模块 | 最末级检查 |
| 其它必填字段 | 该字段的必填检查 |

## 6. 规则4：模块最末级（BUG/建议）

模块路径最后一段必须是叶子节点（三级规格，或无子级的二级/一级）。

| 情况 | 是否最末级 |
|------|:----------:|
| 三级规格 | 是 |
| 二级规格且无三级子级 | 是 |
| 二级规格且有子级 | 否，须选子级 |
| 一级规格且有子级 | 否，须选子级 |
| 一级规格且无子级 | 是 |

## 7. 规则5：关联工艺（BUG）

**触发**：现象描述 / 重现步骤 / 重现条件 / 描述全文含下列任一关键词：  
`激光`、`弧焊`、`焊接`、`切割`、`点焊`、`折弯`、`中厚板`、`冲压`、`码垛`、`搬运`、`熔覆`

**要求**：「关联工艺」必须有值。

**可关闭**：**⚙ 设置 → 校验规则 → 关联工艺校验** 开关可随时启停本规则。关闭后该项输出
`⏭️ 关联工艺校验已在设置中关闭，跳过`，`pass` 为 true，不影响 BUG 的整体通过/不通过结论。
开关状态随其它设置一起持久化到 `login_config.json` 的 `craftRuleEnabled`；
老配置文件没有该字段时按**开启**处理，升级后行为不变。
（「恢复默认」不会重置该开关，避免误点后静默改变校验范围。）

## 8. 附录：模块层级

> 以 `data/规格.json` 为准（校验实际使用的规格表，用户可自行编辑）；缩写一律展开为全称。
> 名称本身含 / 的（如「远程/预约」「TCP/IP」「输入/输出」「登录/注销」）保留原样。
> 与《CrobotpOS测试规格V1.2》命名不一致时，**以该文件为准**（例：摆动工艺、智慧云、CC-Link IE Field从(Anybus)）。
> 该文件损坏或缺失时回退 `src/spec-tree.default.json`，并在页面顶部显示红色横幅。

**自定义规格表**：直接编辑 `data/规格.json`，结构为嵌套的 `name` / `children`：

```json
{
  "specs": [
    { "name": "文件管理", "children": [ { "name": "文件列表" }, { "name": "文件备份" } ] },
    { "name": "独立规格" }
  ]
}
```

- 没有 `children`（或为空数组）= **最末级规格**，校验通过
- 有 `children` = 父级，校验要求改选子级
- `"leaf": false` 可显式声明「这不是最末级」，用于没定义子规格的占位一级（如 `CrobotpLab`）
- 也允许简写：数组元素直接写字符串 `"文件列表"`，等价于 `{ "name": "文件列表" }`
- 反斜杠式路径不受影响：`参数设置/驱动参数/常用参数` 仍按路径解析，取末段判定
- **改完需重启工具生效**；正常加载会在**日志框**打印一行
  （`✓ 规格表已加载：N 个一级规格 / M 个最末级规格`）：页面加载时打一次，
  之后**每次点「运行校验」也重新打印**（该处会清空日志框），保证全程可见。
  JSON 有语法错误时不会崩溃，会回退默认表并在页面顶部显示红色横幅说明原因
