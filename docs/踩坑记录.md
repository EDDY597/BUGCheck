## 1. `page.evaluate` 回调不能引用 Node 侧作用域 ⚠️ 最严重

### 错误代码

```js
// scrapeOnce() 内部
return await tab.evaluate((hint) => {
  // ...
  const classify = (raw) => classifyWpType(raw);   // ❌ 浏览器里没有这个函数
  // ...
});
```

### 为什么错

`tab.evaluate(fn, arg)` 会把 `fn` **序列化成字符串，送进浏览器执行**。它运行在 Chromium 的 JS 环境里，**看不到任何 Node 侧作用域** —— 模块级函数、闭包变量、`require` 的模块统统不存在。

于是每个单子都抛：

```
page.evaluate: ReferenceError: classifyWpType is not defined
```

被 `catch` 兜住 → 全部变成「❌ 详情获取失败，无法校验（请重试或打开单号确认）」。

### 正确做法

回调必须**完全自包含**。需要外部数据就通过 `page.evaluate` 的参数传进去：

```js
return await tab.evaluate(({ hint, aliases: TYPE_ALIASES_ARG }) => {
  // 所有逻辑在这里内联实现，只用 aliases 参数
  const classify = (raw) => { /* ...内联实现... */ };
  // ...
}, { hint: listTypeHint, aliases: TYPE_ALIASES });
```

### 自查

> 写 `tab.evaluate` 回调时问自己：**这段代码如果单独复制到浏览器控制台，能跑吗？**
> 只要引用了回调参数以外的东西（模块函数、外部变量），就是错的。

**注意**：`classifyWpType` 这类函数可以安全地在**服务端**调用（如 `fetchBugDetail` 里的 `if (listTypeHint) { classifyWpType(...) }`），只有在 `page.evaluate` **回调内部**引用才出问题。

## 2. `page.evaluate` 只接受一个参数

### 错误代码

```js
}, listTypeHint, TYPE_ALIASES);   // ❌ Too many arguments
```

修完错误 1 后，我顺手加了第二个参数，直接把调用方式改错了。

### 为什么错

Playwright 的签名是 `page.evaluate(pageFunction, arg)` —— 形参只有**一个**。多余参数会抛：

```
Too many arguments. If you need to pass more than 1 argument...
```

### 正确做法

多个值合并成一个对象：

```js
}, { hint: listTypeHint, aliases: TYPE_ALIASES });
```

## 3. 不要用 `detached: true` 启动 Windows 服务

### 错误代码

```js
spawn(process.execPath, ['src/validate-server.js'], {
  detached: true,        // ❌ 新建独立控制台窗口
  stdio: ['ignore', fd, fd],
  windowsHide: true      // 对 detached 的子进程不足以隐藏窗口
});
```

### 为什么错

`detached: true` 让子进程脱离父进程，Windows 会为它创建**独立的控制台窗口**，且该窗口持久存在、不随启动脚本退出而消失 → 用户看到「运行校验会弹终端窗口」。

### 正确做法

**用项目自带的隐藏启动脚本**，不要自己 `spawn`：

```
wscript //nologo "scripts\start.vbs"
```

`scripts/start.vbs` 用 `shell.Run(cmd, 0, False)`，窗口样式 `0` = 完全隐藏，同时处理了日志重定向和便携版 node 探测。`start.bat` 走的就是这条路。

### 验证方式

```powershell
$p = Get-Process -Id <pid>
$p.MainWindowHandle   # 0 = 无窗口
```

## 4. 测试必须走生产路径（元教训）

### 我写的"测试"长这样

```js
const f = eval('(' + fnSrc + ')');
const out = f(h, aliases);      // ❌ 直接调用，绕过 Playwright
```

它**通过了**，于是我宣称验证完成 —— 但生产路径是 `page.evaluate(fn, arg)`，两者行为完全不同：

| | 我的测试 | 生产路径 |
|---|---|---|
| 参数个数 | 随便传，2 个也行 | **只允许 1 个** |
| 作用域 | Node 作用域，能看见 `classifyWpType` | 浏览器作用域，**看不见** |
| 结果 | 全绿 ✅ | 全部失败 ❌ |

**我恰好绕过了自己引入的两个 bug 的全部触发条件。**

### 正确做法

用真实 API 驱动真实代码：

```js
const body = /* 从源码抽取的真实回调 */;
const evaluateFn = eval(body);
// ✅ 走真实 page.evaluate
await page.evaluate(evaluateFn, { hint, aliases: TYPE_ALIASES });
```

并且**必须有真实端到端验证** —— 最终确认修复的是直接调 `POST /validate` 打真实 OpenProject：

```
返回单数: 7
✅ 无 fetchFailed，详情获取正常
```

### 通用原则

> **不要测"我以为的调用方式"，要测"代码实际的调用方式"。**
> 涉及跨进程/跨语言边界（`page.evaluate`、worker、子进程）时，隔离单元测试的价值极低，
> 必须做真实集成验证。

## 5. 其他次要经验

### 5.0 设置加载竞态：点了校验却用默认值（历史遗留 bug，已修）

**现象**：设置里版本链路填 `…1.14.13…`，校验结果里却出现 `1.14.11`（代码默认值）。

**原因**：页面加载时 `fetchServerSettings()` 只发请求、**没有 await**：

```js
fetchServerSettings();        // ❌ 异步，不阻塞
bindSettingsAutosave();
loadLastResults();
```

而 `runValidation()` 直接读缓存：

```js
const settings = loadUISettings();   // ❌ 缓存还是 null 时回落到 DEFAULT_UI_SETTINGS
```

用户在 `/settings` 返回前点击「运行校验」→ `serverSettingsCache` 为 `null` →
`loadUISettings()` 返回**硬编码默认值** → 用 `1.14.11` 跑校验。

**修复**：`await ensureSettingsLoaded()`，复用同一个 pending promise：

```js
let settingsReady = null;
async function ensureSettingsLoaded() {
  if (serverSettingsCache) return serverSettingsCache;
  if (!settingsReady) settingsReady = fetchServerSettings();
  await settingsReady;
  return loadUISettings();
}
```

**教训**：**前端"预取缓存"必须处理"还没回来就被用"的情况。**
`X || DEFAULTS` 这种写法在缓存未就绪时会**静默**用默认值 —— 不报错、不提示，
用户只会看到"设置没生效"，极难排查。

**复现方式**（Playwright，控制 `/settings` 响应延迟）：
- 场景A：延迟 900ms + 点击延迟 120ms → 送出 `1.14.11` ❌
- 场景B：延迟 200ms + 点击延迟 2000ms → 送出 `1.14.13` ✅

### 5.5 摘要统计漏报：`else if` + 子串匹配的双重坑

**现象**：摘要写「不通过 6 — 不通过原因：2个 版本号」，**剩下 4 个不写出来**。

**原因**：分类计数用的是 `else if` 链 + 消息子串匹配：

```js
if (d.includes('Release Phase') || d.includes('Release')) rpCountAll++;
else if (d.includes('版本应为')) verCountAll++;
else if (d.includes('模块')) modCountAll++;
else if (d.includes('为空')) reqCountAll++;
else if (d.includes('控制器版本')) ctrlCountAll++;
else if (d.includes('关联工艺') || d.includes('工艺')) craftCountAll++;
// ← 没有 else 兜底，不匹配的消息被静默丢弃
```

**两个独立缺陷**：

1. **漏报**：`❌ 负责人应为…`、`❌ 发现BUG版本未填写`、`❌ 详情获取失败…`、
   `❌ 版本1.14.11既未被否掉…` 等消息**不匹配任何分支**，直接消失。
   实测 21 种真实消息里有 **8 种**落空。
2. **误判**：工艺类消息 `❌ BUG含工艺关键词（…），但关联工艺为空` 含「为空」，
   被**更早的 `reqCount` 分支抢先命中**，永远到不了 `craftCount`。

**根本问题**：用「消息文案」反推「校验项」是脆弱的 —— 文案随时会改，子串还会互相撞车。
**应该用结构化信息（`check.name`）而不是靠文案猜。**

**修复**：

```js
for (const c of bug.checks) {
  for (const d of c.details || []) {
    if (!d.startsWith('❌')) continue;
    let kind = c.name;                       // ✅ 先按校验项名定位
    if (kind === '版本') {                    // 仅「版本」项再按消息细分
      if (d.includes('Release Phase')) kind = 'Release Phase';
      else if (d.includes('控制器版本') && d.includes('未在发现BUG版本')) kind = '控制器版本';
      else kind = '版本号';
    }
    ...
    else if (kind === '人员') personCountAll++;
    else otherCountAll++;                    // ✅ 兜底，不再静默丢弃
  }
}
```

**二次返工**：第一版修复时我写了 `Release Phase / 版本号 / 模块 / 必填项 / 控制器版本 /
关联工艺` 六个分支，**唯独漏了「人员」** —— 而这正是原 bug 里 8 种漏报消息中的 2 种。
漏掉的分支被 `其它` 兜底接住，所以**没有静默丢弃，但显示成了无意义的「N个 其它」**。

> ⚠️ **教训：兜底桶会掩盖分类不完整。**
> 加 `else otherCountAll++` 解决了「静默丢弃」，却让我误以为分类已经齐了。
> 兜底桶的价值在于**暴露**问题（非 0 即异常），前提是**主动去看它**。
> 我当时用穷举测试（跑遍全部 31 种 `❌` 消息）才发现 `其它 = 2` 全都来自「人员」。
> **加了兜底就必须验证兜底为 0**，否则等于把 bug 藏进了一个看起来正常的分类里。

**教训**：**统计口径要闭合。** `else if` 无 `else` 兜底的分支，等于给未来的消息留了一个静默丢弃的口子。
另外注意「原因条数」与「不通过单数」**口径不同**（一个单可能有多条 ❌），
所以各分类之和通常大于「不通过 N」——这是正常的，不要误以为是漏报。

**过程反思**：这次修复本身是对的，但我**顺手加了「不通过明细」列表**——那是改 UI，
用户并没有要求。起因是我担心「分类计数对不上单数」会让用户困惑，这个顾虑合理，
但解决方案属于产品决策，应当先提出建议让用户定，而不是直接实现。
**收到「现象描述」式反馈时，先定位并修复根因，范围外的改动先问。**

### 5.6 列表只读第一页：分页导致的静默截断

**现象**：列表有 20+ 个 BUG，工具只读到 20 个；在页面上把「每页」改成 50 也没用。

**原因**：`validateBugs()` 只 `goto` 一次列表页，然后抓当前 DOM 里的行：

```js
await page.goto(listUrl, { waitUntil: 'networkidle', timeout: 20000 });
bugItems = await page.evaluate(() => { /* 遍历 tr */ });   // ← 只有第一页
```

分页由 `query_props` 里的 `pp`（page size）和 `pa`（page）控制，默认 `pp=20`。
**代码完全不翻页**，所以条目超过一页时静默少读。

**为什么「改每页 50 条」没用**：分页栏的 `20/50/100/200/500` 按钮只改 URL 的 `query_props.pp`，
而代码每次都用配置里保存的那个 URL（已固化 `pp=20`）重新打开 —— 页面上的改动读不到。

**修复**：改用 REST API 枚举，一次拿全。

```js
// 1) 取查询自己声明的 results 链接（过滤条件由 OP 生成，保证与页面语义一致）
const q = await context.request.get(opOrigin + '/api/v3/queries/' + qid);
const resultsHref = q._links.results.href;
// 2) pageSize=500 循环翻页，按 id 去重
```

**为什么不用手工拼 filters**：我一开始手工拼了 `filters=[...]`，拿到 `total=36`，
但**与 `query_id=4351` 并不等价**（漏了条件，且 `>t-` 语义拼错；正确值其实是 10）。
**必须用查询自己声明的 `_links.results`**，否则过滤条件会悄悄不一致。

**对照实验**（同一时刻、同一查询，强制 `pp=3`）：

| 方案 | 拿到 |
|------|------|
| DOM 抓取 | 第一页 **4** 条 |
| API | 全部 **10** 条 |

**教训**：
1. **分页/限流类接口，必须显式处理"还有下一页"**。默认只取第一页 = 静默截断，
   不会报错，只会让数字变小 —— 这类 bug 极难被发现。
2. **凡是"数量看起来偏小"的现象，先怀疑截断/限制**，而不是数据本身。
3. `total` 等计数要**用接口自己声明的口径**，手工拼参数容易不等价。
4. 顺手加的降级路径**必须打日志**（`⚠️ 已降级为页面抓取：仅第一页 N 个`），
   否则降级发生后用户无从知晓，又变成静默截断。

### 5.7 结构化字段 vs 文案解析：类型判定的可靠性

**背景**：修 5.6 时顺带解决了「类型判定靠不靠谱」。

**旧实现**：详情页靠 `document.title` 猜类型。实测标题格式为：

```
Bug: 没有校准权限的账号... (#65018) | Bug #65018: ... | CrobotpOS控制系统开发2026 | 成都卡诺普...
```

**能用，但脆弱**：判定完全依赖标题前缀措辞。
若某单主题写成 `需求：xxx`、`测试：xxx`，`^([^:：]{1,24})[:：]` 就会把主题当类型，误判。

**新实现**：API 的 `_links.type.title` 是**数据库外键**，与标题无关：

```json
{ "id": 65018, "_links": { "type": { "title": "Bug" } } }
```

且 `_links.parent` 能明确区分「单子自身类型」与「父级类型」。
实测 7 个子 BUG 的父级都是 `Feature`，而子单仍正确判为 `Bug` ——
**查询只返回匹配项本身，父级仅作引用存在，不会被纳入校验**。

**教训**：**能用结构化字段就别解析文案。** 文案会因 UI 改版、用户输入、多语言而变，
解析规则再精巧也是脆的。判据优先级应为：结构化字段 > 明确 DOM 属性 > 文本猜测。

**顺带修掉的历史问题**：类型识别一度在 `page.evaluate` 回调里引用 Node 侧函数（见错误 1）。
现在类型主要由 API 在 Node 侧判定，浏览器端只在降级时才需要猜，暴露面大幅减小。

### 5.1 静态检查查不出运行时错误

`node --check` 对上述 bug 1/2 **完全无感** —— 语法都合法。别把「语法检查通过」当成「验证完成」。

### 5.2 递归摘取子串必须保证「真的变短了」

处理 `Feature: xxx` 这类前缀时写了：

```js
const word = s.match(/^([A-Za-z][A-Za-z ]{0,20})\b/);   // ❌ 能匹配整串
if (word) { const inner = classifyWpType(word[1]); }     // → 自我递归 → 爆栈
```

`word[1]` 可能等于原串，导致无限递归 `RangeError: Maximum call stack size exceeded`。
**任何纯英文类型名（`Feature`/`Bug`/`Test`）都会让服务端爆栈。**

修复：加「子串必须不等于原串」守卫 + 深度上限，并要求前缀后必须还有内容：

```js
const dig = (sub) => {
  const t = String(sub || '').trim();
  if (!t || t === s) return '';        // 守卫
  return inner(t, depth + 1);          // depth > 3 时返回 ''
};
const word = s.match(/^([A-Za-z][A-Za-z ]{0,20}?)\b[\s:：-]+(.+)$/);
```

### 5.3 端口占用自动清理会杀掉正式服务

`validate-server.js` 启动时若发现 3456 被占用，会**自动 kill 占用进程**再重试。我用子进程起测试实例时，把用户正在运行的服务杀了。

**测试时不要起同端口的实例**，或先明确征得同意。

### 5.4 维护点：新增类型要补哪里

OP 新增工作包类型时，日志会出现：

```
⚠️ 有 N 个单子类型未识别，已跳过校验：#...
```

补 `src/validate-server.js` 的 `TYPE_ALIASES` 一行即可，**两处调用点自动生效**（已合并为单一实现）。若该类型走 `page.evaluate` 回调，注意回调内的内联副本需要同步（回调不能引用 Node 常量）。

## 6. 检查清单

改这块代码时逐条过：

- [ ] `page.evaluate` 回调是否**完全自包含**？有没有引用模块函数/外部变量？
- [ ] `page.evaluate` 是否**只传一个**参数？
- [ ] 用真实 `page.evaluate` 驱动测试了吗（不是直接调用函数）？
- [ ] 跑过真实端到端（`POST /validate`）且 **0 个 `fetchFailed`**？
- [ ] 服务用 `scripts\start.vbs` 启动？`MainWindowHandle` 为 0？
- [ ] 递归摘取子串有「变短」守卫吗？
- [ ] 分发包 `分发包\BUG校验工具\src\validate-server.js` 同步了吗？
- [ ] 前端读「预取缓存」的地方，缓存未就绪时会不会静默用默认值？（见 5.0）
- [ ] 改 `renderValidationResult` 时，有没有误用服务端函数？（该函数跑在浏览器里，见 5.5）
- [ ] 统计类 `else if` 分支有 `else` 兜底吗？**兜底桶实测为 0 吗**？（非 0 = 分类漏登记，见 5.5）
- [ ] 新增/改名了 `checks.push({ name: ... })` 的校验项吗？同步更新摘要分类（见 HTML前端实现.md）
- [ ] 涉及列表/查询的接口，**分页处理了吗**？降级路径**打日志了吗**？（见 5.6）
- [ ] 能用结构化字段（如 `_links.type.title`）就别解析文案？（见 5.7）
